01 / Two sides of protection

Before it lands.
After it’s installed.

Prevention and detection share the same evidence.
Use them together, wherever you build.

01 — PREVENT

Make installs
answer to your policy.

Check resolved dependencies against malicious-package reports, release history, source patterns and your allow/deny rules.

  • Evaluate direct and transitive dependencies
  • Refuse incomplete checks under strict policy
  • Recheck approvals against the current rules
chdora gate exec npm install <package>
02 — DETECT

Find the signals
worth investigating.

Audit existing projects for known malicious packages, suspicious changes, integrity metadata drift and signs of host compromise.

  • Check inventory against OSV and incident packs
  • Look for credential-collection patterns
  • Bring findings into CI with JSON and SARIF
chdora scan .

03 / Security you can inspect

No black box.
No blanket promises.

Read the source ↗
01

The evidence comes with it.

Named checks, package identities and reviewable findings. Suspicious behavior is a signal to investigate, not proof of compromise.

02

Your workstation stays yours.

A single Go binary with no telemetry. Registry-backed checks make network requests; fleet reporting is a separate, opt-in workflow.

03

The boundary is explicit.

The gate is not a runtime sandbox. Some install forms pass through, and installed-file checks are not complete byte-level verification.
