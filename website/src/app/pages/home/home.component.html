chaindora is an open-source CLI and HTTP server that sits between you and the package registry, blocks compromised installs at the gate, and continuously watches what's already on disk. One static Go binary. Apache-2.0. No telemetry.

Before install. After install.

chaindora is a single binary that operates at two moments in the supply chain. The two modes share findings, fix plans, and the incident pack — use either on its own, or both together.

Before install

chdora gate

Sits between the package manager and the registry across 42 package managers in 20+ language ecosystems. Resolves the full transitive install tree, runs every node through ten independent checkers for malicious flags, cooldown, publisher / maintainer churn, provenance, obfuscation patterns, and content-hash republish detection — and refuses the install if any node fails. 

$ npm install some-package
chaindora gate: BLOCKED
  └─ cooldown:    published 4h ago (threshold 72h)
  └─ static:      obfuscated payload in postinstall
  └─ publisher:   different _npmUser since prior version

Fail-closed: any check that can't run treats the install as suspect.

After install

chdora scan · audit · forensics · ci

Finds compromise already on disk across 32 inventory ecosystems. Four entry points that differ only in what populates the inventory: one project tree, the whole host, every project under $HOME, or a CI gate tuned for sticky PR comments and baseline-aware fail-on. Predictive signals (v0.15) replay gate-style behavioral checks against installed packages — cooldown, publisher-change, maintainer-trust, republish- guard — plus lockfile-vs-disk integrity drift on every JS/Rust/Go/ Python ecosystem. 

$ chdora scan .
[CRITICAL] [osv-ioc] request@2.88.2
  └─ GHSA-p8p7-x288-28g6  prototype pollution
[CRITICAL] [incident-pack] shai-hulud worm artifact
  └─ .github/workflows/shai-hulud-workflow.yml

Same finding format, same fix-plan runner, same outputs everywhere (text · JSON · SARIF · PR-comment).

What chaindora catches

Prevention and detection cover overlapping but distinct attack surfaces. Some classes can only be stopped at install time. Others only become visible afterwards. A few — the most dangerous — get caught by either.

Both modes
  • Packages in the OpenSSF Malicious Packages feed (MAL-*)
  • Known CVEs on dependencies (GHSA-* / CVE-* via OSV.dev)
Before install only
chdora gate
  • Cooldown Versions published less than 72 h ago.
  • Account takeover or anomaly Publisher changed since the last release, brand-new accounts, single-version maintainers, multi-year dormancy gaps.
  • Sleeper patterns Obfuscation, install-script payloads, eval-of-dynamic, base64-encoded URLs.
  • Suspicious version-bump diff New postinstall, new child_process import, new outbound URL.
  • Unsigned packages Missing sigstore / sumdb / GPG attestation.
  • Mutable Git-URL deps No registry, no signing — branch refs over http://.
  • Republished bytes Known name@version reappearing with a changed content hash — maintainer-account takeover signal.
After install only
chdora scan / audit / forensics / ci
  • Compromised CI components Unpinned actions, curl-pipe-shell in scripts.
  • Host-state compromise Leaked tokens, shell-rc tampering, worm artifacts on disk.
  • Trust-anchor drift .npmrc, pip.conf, git insteadOf, /etc/hosts, CA store.
  • Post-compromise persistence cron, launchd, systemd, Scheduled Tasks.
  • Extension takeovers Browser, VS Code, IDE extensions installed without your knowledge.
  • Lockfile-vs-disk drift Code in node_modules/<pkg> doesn't match the lockfile-recorded hash.
  • Lockfile MITM go.sum vs sumdb mismatch, Cargo.lock checksum drift.

Sleeper attacks that masquerade as legitimate code for years (xz-utils class) only become visible after community detection lands — the continuous-detection layer catches them retroactively, on the machines and projects that already have them on disk.

Install in 60 seconds

Three steps. No daemons, no background agents, no telemetry to opt out of.

1

Get the binary

Pre-built archives for macOS / Linux / Windows on every release.

curl -L https://github.com/alessandro-bitetto/chaindora/releases/latest/download/chaindora_{{ version }}_$(uname -s | tr A-Z a-z)_amd64.tar.gz | tar xz
sudo mv chdora /usr/local/bin/

From source instead: go install github.com/alessandro-bitetto/chaindora/cmd/chdora@latest

2

Activate prevention

Drops a shim ahead of 42 package managers — npm / yarn / pnpm / bun / deno, pip / poetry / uv / pipenv / pdm / conda, mvn / gradle / sbt, dotnet / paket, composer, cargo, go, bundle / gem, pod / swift / dart / flutter, mix / rebar3, stack / cabal, brew, conan, vcpkg, opam, julia, R, and more.

chdora gate install
export PATH="$HOME/.chaindora/bin:$PATH"  # add to your shell rc

Every package-manager install resolves through chaindora's checkers from here on.

3

Run detection

One project, the whole host, or a CI gate — pick the surface you care about.

chdora scan .                                  # one project
chdora audit --whole-machine                   # everything under $HOME + host state
chdora ci . --baseline ./.chdora-baseline.json --sarif out.sarif

One dashboard. Every machine.

When chaindora runs across multiple developer machines and CI nodes, chdora server aggregates their findings into a single JSON-backed store with a built-in dashboard.

  • One binary serves both the API (/api/v1/*) and the dashboard at /
  • No external DB — JSON-backed state on a single file
  • Per-agent bearer tokens stored as SHA-256 at rest; raw shown once on enrollment
  • Bring-your-own TLS — caddy / nginx / Cloudflare Tunnel
# Server box
chdora server start --addr :8080 \
  --enrollment-secret RANDOM

# Each agent
chdora agent enroll \
  --server https://chaindora.corp:8080 \
  --enrollment-secret RANDOM
chdora watch --interval 1h

Suitable for tens-to-hundreds of agents on the JSON-backed store; a SQL backend is on the roadmap for larger setups.
